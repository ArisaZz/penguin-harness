As a project grows, every local change has to respect more existing requirements. When a coding Agent works on a task, its context often lacks early design decisions and module dependencies. **A change that works on the surface can quietly break rules that other modules rely on**.

To make project rules hold up across iterations, a team has to record long-term design requirements in the repository and back them up with shared implementations, runtime checks, and automated tests. Here we walk through three examples from the PenguinHarness codebase and test suite to show how concrete rules take hold at a write entry point, an approval entry point, and a shared implementation.

## Why chat instructions alone fall short

Concrete rules need those entry points and shared implementations because a single session has a limited context window, leaving existing conventions outside the active context. When an Agent edits a local feature, it may not see the earlier design decisions behind that code. If you only state a requirement in one conversation prompt, that chat message does not automatically become a rule that later sessions can rely on.

We think teams should store long-term design requirements and the reasons behind them in repository docs such as `AGENTS.md`. Different tools have different conventions for loading rule files. When starting a session, a developer needs to load those docs through their tool's mechanism, or tell the Agent in the task prompt to read the relevant docs first, giving code changes a stable basis.

Even when the Agent reads the repository docs, prose can only guide model reasoning. Documentation cannot block a violating call at runtime, and it cannot stop a later commit from breaking an existing implementation while touching another feature. Dropping a document into the repository does not mean the rule is enforced.

**A useful project rule states the behavior to preserve, the reason it exists, and the code path and test that enforce and check it**.

## Turning project rules into code and tests

Naming that code path and test is what moves a project rule from documentation into execution. Repository docs explain design intent, shared code standardizes behavior, runtime checks reject covered violations on the spot, and automated tests check whether covered behavior regresses when the test suite runs. **This combination works only when sessions read the docs, calls go through the shared code paths, and the tests actually run**.

To spend developer time well, our bet is a three-layer pyramid that divides review attention and code responsibility. At the top sit a small number of core rules that humans review closely; temporary task details do not belong in long-term rules. The middle layer holds the stable interfaces and entry points that calls must pass through, and the bottom layer holds the many concrete implementations and components.

A single rule cuts across all three layers, and automated tests check how they behave together. Take the rule that session history must be preserved: the top layer states that history records are never rewritten in place, the middle layer defines a single write entry point, the bottom layer appends to the file, and the test inspects the files after writing[^1]. Even with tests in place, bottom-layer changes that touch data mutations or permissions still need human review.

## Protecting Trace history with append-only writes

**Debugging and session recovery depend on complete history, so never overwriting existing records in place sits at the top of the rule pyramid as a core rule**[^2]. In PenguinHarness, a Trace is the record of session messages and events, including tool calls and approval decisions, used later to read history and resume sessions. If writing code modified or overwrote existing records in place, developers would lose reliable history when debugging or resuming a session, which is why protecting earlier records from modification is a core rule.

To enforce this rule, PenguinHarness puts Trace writing logic inside the shared `Writer`. When a message needs to be recorded, `Writer` opens the target file in append mode. It writes each new record at the end of the file without altering existing content. When a session needs to switch context shards, the program calls `rotate()` to pick a new file for subsequent writes, never rewriting the old file through this write path.

To check this entry-point behavior, `trace.test.ts` inspects the file state and record counts before and after rotation[^3]. The test writes 2 records to the first file, then calls `rotate()` to switch to a second file and writes 1 record. Next, `trace.test.ts` checks that the two file paths differ, the new file holds 1 record, and the original file still holds its initial 2 records. This append-only guarantee covers writes that go through `Writer`; whether an external program with filesystem permissions modifies the file directly is a separate concern.

## Blocking disallowed tool calls at the command execution entry

Beyond protecting written session records with `Writer`, the system also has to check whether a model's tool call request is allowed before handing it to the execution environment to run[^4]. **To keep permission checks from scattering across business logic and drifting out of sync, deny rules belong at the single entry point right before tool execution**.

In PenguinHarness, command policy takes effect at the session execution entry `Session.run`[^5]. The host application integrating the Agent supplies an approval decision, while the command policy checks enabled deny rules first. When a shell command requested by the model matches an enabled deny rule, the policy check rejects the command before asking the application for approval, so a deny-rule match overrides host approval. Only when a command does not match any deny rule does the request move on to the approval flow.

To verify this entry-point block, `command-policy.test.ts` passes an always-allow approval callback and a counting execution environment into a real session[^6]. In the test, a mock model requests a shell command that matches a deny rule. `command-policy.test.ts` then verifies that the approval callback is called 0 times, the execution environment is called 0 times, and the returned message contains the policy-denied decision. Command policy matches the command text of the shell tool to catch accidental misuse. Dynamically computed commands or other execution methods may fall outside what it matches, and runtime access isolation is handled separately by the sandbox boundary.

## Centralizing repeated shared icons

**Just as command policy centralizes permission checks at an entry point, UI elements shared across multiple views need to live in a single shared file**. During day-to-day frontend work, an Agent or developer can finish a local view quickly by copying and pasting code, breaking consistency across the app. Test history in PenguinHarness shows that the brain icon representing memory was once hand-coded in three separate places: the panel, the memory change card, and the Agent card[^7]. When a developer redrew the icon in one spot, the other two kept the old shape.

To prevent partial updates across copies, PenguinHarness moved the memory brain icon definition into the shared file `icons.ts`. The project also set a rule that the known SVG path fragment for this icon may appear only in that file. The test file `icon-scale.test.ts` scans frontend and component library source files for the SVG path fragments of the memory brain icon and several other known icons. It verifies that each path fragment appears only in its designated shared file. If someone hand-writes or pastes that known path string into another component, the test fails.

This source scan matches known path strings, so it catches direct copies of known icon code and cannot detect a newly drawn icon that merely looks similar. Extracting shared code should also follow actual reuse: only implementations genuinely used in multiple places belong in a shared file, without building general abstractions ahead of time for one-off details.

## Growing rules and daily checks from real bugs

The fact that a source scan only catches copy-pasted known icon paths shows why automated tests have to evolve alongside real problems the team hits. Tests can take over plenty of repetitive checking, yet each test only proves that the specific behavior it covers works as expected; a passing test suite does not mean every unknown case is safe. Developers still need to spend their review attention on high-risk changes, checking whether design assumptions hold, permission boundaries stay tight, and data writes remain safe.

In daily iteration with a coding Agent, when the same kind of bug happens more than once, we recommend reproducing the failure locally first and pinning down the expected behavior. Then update the shared implementation or entry-point check and add or update the automated test alongside it.

After changing the code, verify that the test fails on the unpatched behavior and passes with the fix in place. Then wire the test into CI (automated checks run on code changes) so it runs on every change.

**Project rules, shared code, and automated tests have to evolve together as requirements change**. When a legitimate new requirement calls for changing existing behavior, the team should review and update the rule docs, code implementation, and test cases together in the next change.
